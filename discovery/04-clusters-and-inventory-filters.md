# 04 — Clusters and Inventory Filters

ADM produces two kinds of grouping:

- **Clusters** — workspace-local groupings of workloads ADM
  identified as behaving together.
- **Inventory filters** — reusable label expressions that
  resolve to sets of workloads, usable across many policies.

Understanding when to leave a cluster as a cluster vs. when to
promote it to an inventory filter is one of the highest-leverage
decisions in an ADM-driven policy build.

> **Cisco source.** [Manage Policy Lifecycle — Grouping Workloads: Clusters and Inventory Filters](https://www.cisco.com/c/en/us/td/docs/security/workload_security/secure_workload/user-guide/4_0/cisco-secure-workload-user-guide-on-prem-v40/manage-policy-lifecycle-in-secure-workload.html#grouping-workloads).

---

## Clusters

A cluster is what ADM creates when it finds a group of workloads
exhibiting similar communication patterns. Properties:

| Property | Value |
|---|---|
| Scope | Workspace-local — exists only within the workspace ADM ran in |
| Membership | A list of specific workloads (computed at ADM run time) |
| Naming | Auto-generated by ADM (e.g. `Cluster-13`, sometimes with a hint based on tier label) |
| Reusability | None — referenced only by policies in this workspace |
| Stability | Re-computed on each ADM run; membership may shift |

Clusters are useful for *"this workspace's policies"* but not for
the long term. Two reasons:

1. They don't survive across workspaces — a *web cluster* in
   `payments-api` is different from a *web cluster* in
   `crm-web`. Each workspace has its own.
2. Membership is computed by ADM, not derived from a stable
   label expression. As workloads are added, removed, or
   re-labelled, the cluster membership may drift unexpectedly.

---

## Inventory filters

An inventory filter is a **label expression** that resolves to a
set of workloads. Properties:

| Property | Value |
|---|---|
| Scope | Lives at a scope (often a parent scope) — usable from any descendant workspace |
| Membership | Whatever currently matches the label expression — *dynamic* |
| Naming | You name it (`prod-payments-api-web`) |
| Reusability | High — referenced by many policies, often across workspaces |
| Stability | Stable as long as labels are stable |

Inventory filters are how you express *"the web tier of
payments-api in production"* in a way that survives scaling,
re-IP'ing, instance replacement.

---

## Cluster → inventory filter promotion

The natural progression in ADM-driven discovery:

```
   ADM run                                      Workspace
      │                                            │
      ▼                                            ▼
   Cluster-7 = {web-01, web-02, ..., web-12}   ────► used in workspace policies
      │
      │ promotion
      ▼
   Inventory filter: payments-api-web
   = (application=payments-api AND tier=web AND environment=prod)
                                                    │
                                                    ▼
                                          ────► used in workspace policies
                                                AND in other workspaces
                                                AND in cross-scope rules
```

When to promote a cluster to an inventory filter:

| Promote when | Keep as cluster when |
|---|---|
| The cluster represents a stable workload role (web, app, db) | The cluster represents a transient ADM finding you'll resolve via labels next iteration |
| Other workspaces will need to reference it (e.g. cross-scope rules) | The grouping is purely workspace-local |
| Membership can be expressed as a clean label expression | Membership can't be expressed in labels (you'd need to enumerate workloads — a sign the labels are wrong) |
| You expect membership to grow / shrink over time | The current membership is exact and unlikely to change |

> **Practical rule.** If the cluster maps cleanly to
> `application=X AND tier=Y AND environment=Z`, promote it.
> If it doesn't, fix labels until it does, then promote.

## Naming inventory filters

Names matter — these are referenced from policies that humans
will read for years.

Recommended pattern:
`{environment}-{application}-{role}` — e.g.
`prod-payments-api-web`, `prod-payments-api-db`,
`prod-shared-dns`, `dr-mongo-replica`.

Anti-patterns:

| Don't | Why |
|---|---|
| `Cluster-7-promoted` | Tells the reader nothing |
| `payments-api-web-corrected-2026q2` | Datestamps in names rot |
| `web` | Ambiguous — which app's web? |
| `Pawel's-filter` | Personal names rot when Pawel rotates teams |

---

## Inventory filters at the right scope

An inventory filter should live at the **lowest scope from
which all its consumers can reach it**.

| Filter | Should live at | Why |
|---|---|---|
| `prod-payments-api-web` | `payments-api` scope | Only payments-api policies reference it |
| `prod-shared-dns` | `Production` scope | Every prod app references it |
| `prod-shared-monitoring` | `Production` scope | Every prod app references it |
| `regulatory-deny-target` (e.g. `data_classification=public`) | Tenant root | Used in tenant-wide Absolute Deny |

Putting the filter too high (tenant when it should be on
`payments-api`) creates clutter; putting it too low (on
`payments-api` when the parent scope wants to use it) creates
duplication.

---

## When clusters mismatch your mental model

If ADM produces clusters that don't match how you understood the
app, that's a signal — usually one of:

| Cluster shape | What it usually means |
|---|---|
| One giant cluster covering all tiers | Inventory missing `tier` labels — flow patterns alone weren't enough to separate |
| Tier 3 split into A and B clusters | Two real sub-roles within tier 3 — investigate, possibly add `subtier` label |
| A workload appearing in two clusters | Should be impossible in one ADM run; if you see it, it's an artefact of run-comparison view, not membership |
| Workload alone in its own cluster | Either a real outlier (and the labels should reflect it) or it was offline for most of the window |

In every case, the right move is to **fix the underlying
inventory state and re-run ADM**, not to manually edit cluster
membership in the UI.
